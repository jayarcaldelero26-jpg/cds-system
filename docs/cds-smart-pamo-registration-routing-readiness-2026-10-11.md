- `effectiveCategory()` recognizes the string `PAMO`, but `OPERATIONAL_CATEGORIES` excludes it (`OrganizationalAccessService.php:37,499-503`). `validateAssignment()` rejects a category outside that list before its PAMO branch can run (`:637-661`). `UpdateUserRequest` conditionally allows a legacy PAMO category and returns before assignment validation when an existing PAMO user remains PAMO (`UpdateUserRequest.php:24-49,52-75`).
- PAMO normalization clears the unit and may fill `office_designated` with the supervising office. `effectiveUnits()` then returns no Conservation unit for a PAMO user (`OrganizationalAccessService.php:128-137,504-540`). This blocks the route middleware and source authorization paths that depend on Conservation scope. A PAMO-specific branch in `EnsureOrganizationalUnit.php:25-32` only covers PAMB GET requests and does not repair the general scope or write authorization.
- `hasSubmissionTrackingScope()` also requires a category in `OPERATIONAL_CATEGORIES` (`OrganizationalAccessService.php:95-102`). The PAMO `canViewSubmissionTracking()` branch requires an explicit `submission-tracking.view` permission (`:104-110`), but that permission is not in the checked-in `PermissionSeeder` permission list and PAMO is not passed through its category permission-profile loop (`PermissionSeeder.php:84-139,153-164`; `OrganizationalAccessService.php:490-496`). The application gate only grants Conservation read access through `canBrowseModuleUnit()` (`AppServiceProvider.php:70-77`), which currently fails for PAMO.
- `technical-reports.create/update` are gated to CENRO focal preparation for PA-bound submissions; there is no PAMO branch (`AppServiceProvider.php:88-103`; `OrganizationalAccessService.php:187-200`). The existing PAMO `submit` checks in `PambSubmissionAccessService.php:122-150` are therefore not a complete permission path.
- `approve()` currently flips `is_approved` and `is_active` without revalidating the organizational assignment (`Admin/UserController.php:299-330`). `activate()` uses `operationalCategories()`, which excludes PAMO (`:211-254,419-445`). Future approval must validate and persist the approved PA/PAMO relation before activating the pending user. `UserPolicy.php:10-33` plus the `admin` route group in `routes/web.php:250-260` put account approval behind administrators; a registrant cannot approve their own account.
- PA supervising-office assignment is already managed server-side by `assignSupervisingOffice()`, with global-administrator or `protected-areas.create/update` authorization (`OrganizationalAccessService.php:385-390`; `ProtectedAreaController.php:56-82`). Add PAMO mapping to the same controlled PA administration flow. An administrator approves the user-to-PA request through account approval; an authorized PA administrator maintains the PA-to-PAMO office mapping. These are separate approvals.
- Validate the full relationship on the server at registration and again under lock at account approval and report start. The submitted PA ID must resolve to the same active PAMO office mapping used for routing. Derive the CENRO from the PA's current approved supervising assignment for CENRO-affiliated areas. For MHRWS, keep the direct profile and an absent CENRO assignment. A missing normal-PA CENRO mapping should fail closed.
- Routing-position disabled categories currently concern only Office of the PENRO and PENRO TSD Chief (`RoutingPositionSettingsService.php:51-79`). PAMO registration should not be hidden or authorized based on those downstream switches.

### Minimum organization data reuse

Reuse `organizational_offices` (`id`, unique `code`, `name`, `office_type`, `is_active`) and `protected_area_office_assignments` (`protected_area_id`, `organizational_office_id`, `assignment_type`, `assigned_by`). The existing unique key on `(protected_area_id, assignment_type)` supports one `pamo` mapping and one separate `supervising` mapping per PA (`2026_09_03_140000_create_organizational_offices_and_pa_assignments.php:11-42`). Represent a PAMO office as `office_type=pamo` and its PA relation as `assignment_type=pamo`; retain the supervising CENRO/PENRO relation independently. One office ID can serve multiple assigned PA rows and many individual users. Keep `ProtectedArea.pamo` as legacy display data only; it is not an authorization key.

The present protected-area UI exposes only the supervising office (`ProtectedAreaController.php:51-80`; `ProtectedAreas/Form.jsx`). Add an administrator-managed PAMO office selector/mapping there, with active office types validated server-side. Extend office options by ID/type instead of broadening a user-controlled text field.

### Handoff and receipt semantics

Use a distinct transit stage for each outbound transfer and keep the recipient's `Receive` action separate. For a regular PA the new first pair is:

`PAMO start -> forward_from_pamo_to_cenro_focal -> transit_to_cenro_focal -> receive_at_cenro_focal -> existing CENRO preparation stage`

For MHRWS reuse the existing pair:

`PAMO start -> forward_from_pamo -> transit_to_penro_records -> receive_at_penro_records -> existing direct PENRO route`

Do not use the new generic PAMO handoff to skip CENRO for other PAs. The route must be selected from the immutable PA route context, never from a posted destination or group value.

`EffectiveRoutingGraphResolver.php:14-55` applies the captured Office/TSD settings and constructs the PENRO dispatch variants. For MHRWS, after PENRO Records has received the PAMO handoff, retain all four current downstream combinations:

| Office of PENRO | PENRO TSD Chief | First PENRO Records dispatch after receipt |
| --- | --- | --- |
| Included | Included | Forward to Office of PENRO -> Receive -> assign to TSD -> Receive -> forward to CDS Focal -> Receive |
| Excluded | Included | Dispatch to TSD -> Receive -> forward to CDS Focal -> Receive |
| Included | Excluded | Forward to Office of PENRO -> Receive -> dispatch to CDS Focal -> Receive |
| Excluded | Excluded | Dispatch directly to CDS Focal -> Receive |

The existing downstream PENRO focal/chief and final release path follows each branch. Keep the required synchronous archive checkpoint at the existing first dispatch from PENRO Records: `ArchiveCheckpointPolicy.php:7-24` only treats the current PENRO Records dispatch actions as that checkpoint. A PAMO handoff must not replace or bypass it.

### PAMB MOV gate and correction ownership

- Conservation create currently requires the report's MOV upload in the same `store()` request; there is no partial draft state (`ConservationReportSubmissionController.php:71-97,153-181`). The handler persists the report and uses the protected document replacement service before it returns success.

Keep `RoutingTransitionLifecycle.php:17-34` and the PENRO dispatch archive lifecycle intact. Preserve stale-action checks, row locks, duplicate guards, route attachment replacement rules, and document/source identity.

## 3. PAMO clock, TAT projection, and cutover

### Timing contract

1. **Start:** the server's first successfully persisted `PAMO preparation started` event for that source record. Persist the timestamp in the application's Manila timezone with the authenticated user ID and captured PA/PAMO office identity. Registration, login, selecting a file, upload-only history, activity/accomplishment dates, and historical dates are not start evidence.
2. **Initial end:** the accepted outbound PAMO handoff event: CENRO Focal for a normal PA, PENRO Records for MHRWS. A click or client request is not an accepted end; the transition service must validate current state and actor under its existing source-row lock before appending the event.
3. **Recipient start:** CENRO Focal or PENRO Records processing starts only on that destination's accepted `Receive` event. A PAMO outbound event never stands in for the recipient receipt.
4. **Corrections:** a PAMO correction segment begins at accepted `Receive Correction` and ends at the next accepted PAMO handoff. Sum valid PAMO-owned segments once per report for the PAMO office sample. Saves, MOV replacements, and repeated submission requests do not reset the first start or create another document sample. An unfinished or invalid interval remains pending/missing evidence; it is never coerced to zero.
5. **Attribution:** store the report PA separately from the office whose interval is measured. PAMO aggregation uses stable `pamo_office_id`, not one row per account. CENRO interval ownership remains its office across internal focal/chief/records transfers; MHRWS has no CENRO interval before PENRO receipt.

### Draft state and report completeness

The current Conservation `store()` operation is create-plus-required-MOV, while the routing handoff occurs separately. There is no persisted draft or preparation event today. Treat `Save Draft / Start Report` as a real server-side persistence operation: create the draft/source identity and immutable origin snapshot once; allow required report fields/MOV to be completed afterwards; validate all existing workflow fields and required MOV before the first handoff. The first successful persistence starts the clock. If partial drafts are not allowed, the existing full create-plus-MOV operation could be the start, but the metric would measure only the fully-prepared wait-to-handoff interval, not report drafting. Do not describe it as end-to-end preparation time.

Use the append-only `document_routing_events` contract (`event_key`, stages, office labels, `occurred_at`, `recorded_by`, JSON metadata) for the preparation-start event if its lifecycle is extended safely; otherwise add a dedicated append-only origin-event record. Event metadata should carry the source identity and captured snapshot reference, while the snapshot supplies immutable office and PA IDs. Ensure the first event, route snapshot, and origin context are created once in one DB transaction. Use source-row locking plus an idempotency key/unique constraint so retries do not make extra starts or samples. No separate event should pretend the recipient has received custody.

### TAT projector changes

The current working-tree `OfficeTatAnalyticsService` defines live office TAT as accepted office receipt to accepted next handoff and combines correction segments per document (`OfficeTatAnalyticsService.php:185,587-683`). Its live sample discovery starts from `received` events (`:249-265,308-363`) and it does not treat an origin-start event as a PAMO receipt. Its current PAMO identity path uses editable names and user fallback (`:568-583,810-832`), while office configuration stores an office string (`OfficeTatConfigurationVersion.php:9-17`; current working migration `2026_10_09_000001...php:51-63`).

Add an explicitly labeled **PAMO preparation TAT** basis to the existing PAMO office row, keyed by `organizational_office_id`. For each report, use the first start-to-handoff segment plus any actual PAMO correction segments, document-weighted once. Keep this basis separate from the existing receipt-to-next-handoff TAT until its definition and score contribution are explicitly configured; otherwise an origin preparation interval and a recipient processing interval would be mixed under different start rules. Count PAMO starts in a separately named started/originated volume measure, not silently as `documents_received`. Keep existing CENRO/PENRO receipt evidence, event paging, document weighting, Manila period cutoffs, semester/annual periods, rank behavior, and manual historical gap projection unchanged. A missing start or handoff stays N/A/missing, never zero. Historical manual date gaps are not office custody evidence.

### Versioning and cutover

- Extend the immutable `SubmissionRoutingSnapshot` with additive origin context: origin kind, PA ID, PAMO office ID, nullable responsible CENRO office ID, originator, and the existing captured setting-version reference. Capture it at the persisted PAMO start, not at a later handoff. The present snapshot table is unique by source/source ID and already records profile and graph version (`2026_10_06_000002_create_submission_routing_snapshots.php:11-23`).
- Version the new semantic route graph separately from the existing Office/TSD setting version. Keep the current v1 resolver and `regular`/`direct` snapshots readable. Add a v2 resolver branch for PAMO-origin context; do not globally change `GRAPH_VERSION` in a way that rejects old snapshots. Current code rejects any non-current graph version or profile outside `regular/direct` (`RoutingPositionSnapshotService.php:126-170`); future compatibility must dispatch by the stored version and fail closed only for genuinely unknown/malformed versions.
- Add an explicit feature cutover for PAMO-origin starts. Only a post-cutover, validated PAMO start can create a PAMO-origin v2 snapshot. Pre-cutover rows, captured or not, keep their current regular/direct/legacy behavior; never infer a PAMO start from current account/PA data or retrofit event history. Downstream Office/TSD settings are captured with the origin snapshot so later setting changes do not alter a new report's graph.
- Keep capture immutable after first persistence. Do not fall back from a captured route to a live settings head or current office mapping. When an office assignment changes later, the existing report continues to use its captured office IDs; new starts use the newly approved mapping.
- Preserve historical exclusion in TAT projection. No pre-cutover report receives a synthetic origin event or PAMO duration.

9. **MySQL concurrency:** add a two-worker MySQL test for concurrent first Start/route capture and duplicate first handoffs. Assert exactly one start event and unique source snapshot, serializable first transition, and safe retry after failure. SQLite cannot prove MySQL row-level `SELECT ... FOR UPDATE`, lock ordering/deadlock behavior, or the same unique-key race semantics. Reuse the existing MySQL concurrency harness rather than claiming SQLite covers this invariant.

## Unresolved business decisions

1. Which source modules are in the first release: Conservation/PAMB only, or every PA-bound source with its own required MOV contract? The common routing registry is shared, but creation, access, and attachment rules differ by source.
2. May a PAMO user save a partial draft before the required MOV/report fields are ready? The recommended clock starts at the first persisted draft; without partial drafts, the clock measures only the interval after a complete report/MOV save.
3. Should PAMO preparation TAT remain a separately labeled measure, as recommended, or contribute to the existing office score/average? If it contributes, the owner must set the scoring weight and decide whether the PAMO started-volume count is a separate measure or part of the existing received-volume denominator.
